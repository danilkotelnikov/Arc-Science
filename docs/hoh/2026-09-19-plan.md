# Loop plan — memory at corpus scale

## Objective

Turn the open "memory scope" gate from an assertion into measurements: how the native
memory worker and the Python capture/reconciliation path behave with a corpus shaped
like real mission captures, at a size a single lab would reach (hundreds of missions,
tens of thousands of records), and whether the documented degradation beyond 100
retained missions is bounded or pathological.

## Scope

- `native/arc-memory`: a corpus-shaped benchmark (explicit, ignored test) covering
  append cost, `session_list`, `session_fetch`, lexical search on common and rare
  terms, the semantic candidate scan and hybrid fusion, plus database size on disk.
  Any defect it exposes gets a regular regression test and a bounded fix.
- `apps/arc-science` memory routes: an opt-in scale test against the real worker
  binary measuring first capture and restart reconciliation of 100 retained missions,
  and the behaviour with more than 100 (status, cost per health read, no crash).
- Ledger: budgets, actual numbers, environment and what the numbers do not prove.

Out of scope: a real embedder (new dependency, not authorized), semantic-quality
evaluation (needs the embedder), UI changes.

## Preserve

Protocol `arc-memory/1`, record identity and idempotency semantics, read budgets
(1000 records / 8 MiB text / 16 MiB frames), the single worker per database, the
capture-never-fails-a-mission rule, and every existing test.

## Acceptance

Measured on this workstation with a synthetic corpus of 200 sessions × 100 records
(70 % short event lines, 30 % 2–8 KiB JSON payloads with shared scientific vocabulary),
recorded as p50/p95 over repeated calls. Budgets are local-desktop thresholds, not
service objectives:

| Measure | Budget |
| --- | --- |
| `session_list` over 200 sessions | p95 ≤ 50 ms |
| `session_fetch` of one 100-record session | p95 ≤ 50 ms |
| lexical search, limit 10, rare and common term | p95 ≤ 50 ms |
| semantic search, 20k candidates, dim 384 | p95 ≤ 500 ms |
| hybrid search | p95 ≤ 550 ms (the lexical and semantic budgets summed); the measured ratio to its own pool-size retrievals is reported |
| append, mixed payloads | mean ≤ 20 ms per record |
| restart reconciliation, 100 missions × ~60 records (idempotent replay) | ≤ 30 s |
| worker RSS after the corpus (if measurable) | ≤ 200 MiB, reported |

Beyond 100 retained missions: capture status reports degraded, the service keeps
serving, and one health read costs at most one bounded replay.

## Dependencies

Existing crates and packages only. Release `arc-memory-worker.exe` for the Python
scale test (`ARC_MEMORY_WORKER`). Independent evaluation by Sol (GPT-5.6, read-only)
on the frozen diff; shared-workspace tooling, no hard isolation.

## Revision — 2026-09-19, after evaluation

The hybrid row originally read "p95 ≤ lexical + semantic", which the first benchmark
implemented as the sum of the *measured* limit-10 latencies. Hybrid runs both
retrievals with a 4× candidate pool, and a 50-round p95 of the fusion exceeded even
the measured pool-size sum by 2.5 %; a moving measured sum is not a budget. The row
now names the fixed threshold (the two budgets summed, 550 ms) and the benchmark
reports the ratio to the pool-size retrievals so fusion overhead stays visible.
